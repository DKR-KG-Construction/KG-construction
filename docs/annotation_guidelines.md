# Proposal TEST annotation guidelines

You label **raw extracted triples** `(head, relation, tail)` shown with the quote the model cited.
You do not see which repair steps kept or dropped a triple, nor the gold annotations. Keep it that way.

Before starting, both annotators should read and agree on these guidelines. Read the full document
in the shared `docs.txt` (search for the row's `doc_id`). Judge against **the document text**, not
against your knowledge of the world.

| Label | Use it when |
|---|---|
| `correct` | the document states the fact, or directly implies it, **with the direction of the relation as described** (see the schema descriptions); the head and tail are the right entities |
| `incorrect` | the fact is not in the document (even if true in the world); the direction is reversed; an endpoint is the wrong entity or the wrong type of thing; the relation does not mean what the schema says |
| `uncertain` | you cannot decide after reading the whole document (ambiguous wording, unclear coreference). Use sparingly; the policy for `uncertain` is set in `config.yaml` (`annotation.uncertain`) |

Rules of thumb
1. **Quote problems are not label problems.** If the fact is right but the quote is paraphrased or wrong, label the *fact* `correct`. Quote validity is measured separately by step P.
2. **Duplicates:** if two entities clearly refer to the same thing, label each triple on its own merits.
3. **Type of the endpoint:** `P27` (country of citizenship) with tail "Berlin" is `incorrect` (a city, not a country).
4. **Dates:** a different granularity (year vs full date) is `correct` only if it does not contradict the text.
5. Write a short reason in `notes` for every `incorrect` and `uncertain`: this becomes the error taxonomy
   (suggested categories: hallucinated fact, wrong direction, wrong entity, wrong type, wrong relation, paraphrase-only).

## This proposal sample

The proposal TEST sample is generated by `bash run.sh proposal-sample` after the frozen TEST
extraction and evaluation. It contains up to 100 unique items for each of the four pipeline stages
(`raw`, `C`, `C+S`, and `C+S+P`), deduplicated across stages. The current sample has 375 unique
items: the primary annotator labels every row in `annotation/proposal_test/annotator1.csv`, and
the second annotator labels the 75 rows in `annotation/proposal_test/annotator2.csv` (20% overlap).
Both annotators use `annotation/proposal_test/docs.txt` to inspect the full source documents.

Work independently: do not discuss labels until both CSVs are complete. Fill only the `label` and
`notes` cells; preserve all headers and `item_id` values. Do not share or inspect
`annotation/proposal_test/key.json` while annotating: it maps items to stages and is used only by
the scoring command.

The current `config.yaml` sets `annotation.uncertain: exclude`, so uncertain labels are reported
but excluded from the manual-precision denominator. Keep this policy unchanged after the TEST
freeze; if the team needs a different policy, resolve it before annotation and re-freeze before
running TEST.

When both files are returned and complete, run `bash run.sh proposal-score`. It validates the
assigned rows, reports per-stage manual precision and intervals plus agreement on the overlap,
and writes `results/proposal_manual_summary.csv`. The older TRAIN pilot/calibration annotation
files are separate and are not inputs to this proposal TEST scoring step.
